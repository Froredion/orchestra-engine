### O-7. Which inputs produce "cannot have destructuring"? `using [a] = b` is the landmine.

**Pinned:** R21 says destructuring patterns produce an error containing
"cannot have destructuring". **Left open:** *which* syntactic forms count. The request
does not distinguish `using {a} = b` from `using [a] = b`, and they are not the same.

**Codebase: points squarely at the wrong answer if copied.** The `let` precedent,
`src/parser.ts:1537`, is the model any implementer will reach for:
```ts
  if (parser.getToken() & (Token.IsIdentifier | Token.IsPatternStart)) {
```
`Token.IsPatternStart` (`src/token.ts:21`) is set on both `[` and `{`. Copying this line for
`using` classifies `using [a] = b` as a declaration with an array-pattern binding — which
then hits the new "cannot have destructuring" error.

**Outside authority says that is a spec violation.** Executed against acorn 8.16.0:
```
{ using [a] = b; }        → OK   ExpressionStatement: (using[a]) = b     ← member assignment
{ using {a} = b; }        → ERR  Unexpected token (1:8)
for (using [a] of b);     → OK   ForOfStatement, left = MemberExpression using[a]
for (using {a} of b);     → ERR  Unexpected token (1:11)
{ using\n[a] = b; }       → OK   same member assignment
```
`using` followed by `[` is a *member access on a variable named `using`*, because `[` is not
an identifier start and the grammar's UsingDeclaration requires a `BindingIdentifier`.
Acorn's guard is `if (!isIdentifierStart(ch) && ch !== 92) return false` in `isUsingKeyword`.

**Consumer impact and asymmetry.** `using` is a perfectly ordinary variable name today
(`test/parser/miscellaneous/commonjs.ts` aside, nothing in this repo uses it, but real code
does — e.g. `const using = new Map(); using[key] = v;`). If the build errors on
`using [a] = b`, it **rejects currently-valid JavaScript**, and does so only when
`next: true`, which is the mode test262 runs in
(`test262/run-test262.mjs` passes `next: true`). If instead the build treats `using [` as a
member expression and never produces "cannot have destructuring" for it, the cost is that
one of the five pinned substrings is reachable only via `using {a} = b`.

**Which direction survives being wrong:** treating `using [` as a member expression. Being
too permissive costs one unreachable-ish error path; being too eager breaks valid input.

**Also genuinely open, and not answered by acorn:** acorn produces a bare
`Unexpected token` for `using {a} = b` — it has *no* dedicated destructuring message. So
R21 is a meriyah-specific requirement with no reference behaviour to copy, and the set of
inputs that should hit it (`using {a} = b`? `for (using {a} of b)`? `using [a] = b`? all
three?) is decided by the implementer, not by the request. I flag this as the requirement
most likely to have been implemented at the wrong *breadth*.
