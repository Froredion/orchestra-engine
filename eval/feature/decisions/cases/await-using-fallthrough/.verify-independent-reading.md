### O-12. `await using` outside async: which error, and is `await` still an identifier in sloppy script?

**Pinned:** R12/R13 pin the message substring and the priority. **Left open:** the
interaction with meriyah's existing `await`-as-identifier handling.

**Codebase: settles the mechanism.** `src/parser.ts:3329`:
`if (context & Context.InAwaitContext || (context & Context.Module && context & Context.InGlobal))`
— that exact disjunction *is* R8's "async contexts or module top-level", already written.
The same disjunction appears at `src/parser.ts:1859` for `for await`. So R8/R9 map onto an
existing, tested predicate with no new state needed. Good news, and worth checking the
build actually reused it rather than inventing a parallel one.

But in sloppy script, `await` is a legal identifier (`Token.AwaitKeyword` is
`Contextual | IsExpressionStart | IsIdentifier`, `src/token.ts:164`), so
`await using x = 1;` at script top level begins as an *identifier expression* `await`
followed by `using` — which is where R13's priority rule bites.

**Outside authority — acorn does the opposite of R13.** In acorn's `parseStatement`, the
`!this.allowUsing` check runs *before* the `!this.canAwait` check, and `raise` throws
immediately. Executed: `await using x = 1;` with `sourceType:'script'` →
`Using declaration cannot appear in the top level when source type is \`script\`…`,
**not** the await message. R13 explicitly requires the reverse.

**Consequence for the next stage:** R13 is a *deliberate* divergence from the reference
implementation. Any part of the build that was written by pattern-matching acorn will have
this backwards, and it will look correct to anyone who checks against acorn. This is the
requirement I would flag as most likely to have been "verified" against the wrong oracle.
